# # Fuzzing
퍼징은 비정상적인 입력을 생성해 프로그램을 반복적으로 실행하는 것이다.  
반복적으로 입력을 주입하면서 크래시나 메모리 누수, 무한 루프, 예외 상황 등의 버그를 자동으로 찾아내는 (동적) 소프트웨어 테스트 기법이다.  
exploit개발이나 침투 테스트, 취약점 분석에서 퍼징이 자주 사용되는 편이다. 

## ## Fuzzing이 필요한 이유
### 인간의 예측 한계 극복
인간은 정상적인 시나리오에서 주로 테스트 케이스를 설계한다. 때문에 극단적인 케이스(Edge Case)나 비표준 입력에 숨어있는 취약점을 놓치기 쉽다.

### 자동화
인간의 개입 없이 초당 수백~수만 번의 입력을 자동으로 테스트할 수 있기에 비용 대비 취약점 발굴 효율이 높다.

### 메모리 오염 취약점 탐지에 특화
버퍼 오버플로우(BOF), Use-After-Free(UAF), 정수 오버플로우, 널 포인터 역참조 등은 크래시를 유발하기에 퍼징을 이용하여 효과적으로 탐색할 수 있다.

# # Fuzzer 
퍼징 프로세스를 자동화하여 수행하는 소프트웨어(도구)이다.  

---

# # 퍼징 프로세스
1. 초기 시드(seed) 준비: 프로그램이 정상적으로 파싱할 수 있는 유효한 초기 입력값 집합 준비
2. 입력 생성(Generation) 및 변이(Mutation): 시드 데이터의 일부를 변조하거나 규칙에 따라 새로운 테스트 케이스 생성
3. 대상 프로그램 실행 및 모니터링: 생성된 입력을 대상 프로그램에 주입하여 실행, 실행 경로와 예외 발생 여부 감시
4. 크래시 탐지 및 저장: 비정상 종료나 응답없음의 경고가 발생하면 해당 입력값을 저장
5. 트리아지[^1] 및 분석: 중복된 크래시를 제거, 크래시가 악용 가능한 취약점인지 분석
[^1]: 트리아지: Triage. 선별. 발견된 버그를 중복 제거하고 우선순위를 정한다. 

# # Fuzzing 결과를 판단하기
보조 도구를 함께 사용해서 퍼징 효율을 판단한다.
## ## Sanitizer(오류 탐지기)
메모리 오염이 발생해도 프로그램이 살아서 넘어가는(즉시 충돌 현상을 일으키지 않는) 경우가 존재한다. 이를 놓치지 않기 위해 ASan(AddressSanitizer), UBSan(UndefinedBehaviorSanitizer), MSan(MemorySanitizer) 등의 도구를 사용해 메모리 안정성이나 정의되지 않은 행동을 감지한다.

---

# # 종류
## ## 내부 정보의 상세도에 따른 그룹 
### Black-box Fuzzer
- 내부 소스코드나 바이너리 구조를 전혀 알지 못하고, 입력과 출력 행동만 관찰한다.
- 구현이 단순하며 실행 속도가 매우 빠르다.
- 깊은 코드 분기나 복잡한 조건문은 통과가 어렵다.

### White-box Fuzzer
- Symbolic Execution(심볼릭 실행)[^2], Concolic Testing[^3] 등을 통해 프로그램 내부 논리와 제어 흐름을 분석하고, 경로 제약 조건을 풀어 테스트 케이스를 생성한다(경로에 도달하는 입력을 계산). 
- 코드의 깊은 곳까지 도달할 수 있다.
- 경로 폭발(Path Explosion)[^4]문제로 속도가 매우 느리다.

[^2]: 심볼릭 실행(Symbolic Execution): 구체적인 값 대신, 수학의 미지수처럼 기호를 집어놓고 코드를 따라가며 실행 경로의 조건식을 수집하는 분석 방법
[^3]: 콘콜릭 테스팅(Concolic Testing): 구체적 실행 + 심볼릭 실행. 심볼릭 실행은 외부 라이브러리 호출이나 복잡한 반복문을 만나면 수학식으로 표현하지 못해 멈추는 한계가 존재. 먼저 실제값을 넣어 프로그램을 정상 실행 시키면서 지나간 경로의 조건을 기록하고, 마지막 분기 조건 하나만 반대로 뒤집어 심볼릭 연산으로 새 입력값을 계산하는 방법 
[^4]: 경로 폭발(Path Explosion): 프로그램의 if문이나 반복문이 늘어날 수록 실행 가능한 경우의 수(경로)가 기하급수적으로 증가해 분석이 사실상 불가능해지는 것

### Grey-box Fuzzer
- Black-box의 빠른 속도와 White-box의 내부 정보를 활용하는 장점을 절충한 방식이다. 소스 코드 전체를 해석하기 보다는 컴파일 타임 계측[^5]이나 동적 바이너리 계측[^6]으로 코드 커버리지[^7] 같은 경량화된 내부 피드백만 수집한다. 

> 계측(Instrumentation)은 퍼저가 지금 실행 중인 입력값이 어느 코드 블록을 지나갔는지 알 수 있도록 프로그램 내부 분기점마다 작은 추적 코드를 심어 넣는 작업

[^5]: 컴파일 타임 계측: 소스코드가 있을 경우 사용. 프로그램을 빌드하는 과정에서 컴파일러가 어셈블리 사이에 추적 코드를 추가
[^6]: 동적 바이너리 계측: 소스코드가 없고 컴파일된 바이너리(실행파일)만 있을 경우 사용. 프로그램을 실행하는 동시에 CPU 명령어를 실시간으로 가로체서 메모리에서 추적코드를 끼워넣으며 실행 
[^7]: 코드 커버리지: 퍼저가 주입한 테스트 입력값들이 전체 프로그램 코드 중 얼마나 많은 영역을 실제로 실행해봤는지 나타내는 지표. 주로 전체 코드 줄 중 실행된 줄의 비율(line), 분기 없이 순차적으로 실행되는 기본 블록 중 실행된 블록의 비율(Basic Block), A에서 B블록으로 이동하는 흐름(Edge Coverage)—블록과 블록을 잇는 화살표 하나하나—로 자주 측정

## ## 입력 생성 방식에 따른 그룹
### Mutation-based Fuzzer(변이 기반 퍼저) 
- Dumb Fuzzer라고도 한다. 
- 준비된 입력 시드를 기반으로 비트 반전, 바이트 추가 삭제 등 무작위/휴리스틱 변형을 가해 새 입력을 만든다. (즉, 이미 생성된 값에 대해 특정한 조작을 가해 값을 변조하는 것)
- 입력 형식(포맷)에 대한 사전 지식이 없어도 바로 적용 가능하다.
- 체크섬이나 업격한 문법 구조를 가진 포맷의 경우 초기 파싱 단계에서 대부분 걸러지기에 깊은 로직까지의 도달이 어렵다.

### Generation-based Fuzzer(생성 기반 퍼저)
- Intelligent Fuzzer라고도 한다.
- 대상 프로그램이 요구하는 입력 데이터의 명세(프로토콜 규격, 파일 포맷 문법...)를 미리 정의헤 두고, 그 규칙에 맞는 테스트 케이스를 처음부터 새로 생성한다.
- 문법 오류로 초기에 거부되지 않고 프로그램의 깊은 로직까지 도달할 확률이 높다.
- 입력 명세 작성에 많은 시간과 사전 분석 비용이 요구된다.

# # 대표적 Fuzzer
## ## AFL / [AFL++](https://github.com/AFLplusplus/AFLplusplus)
- Grey-box Fuzzer (Coverage-guided, 변이 기반)
- AFL++은 원작 AFL의 개발 중단 이후 커뮤니티가 주축으로 변이 전략, 스케줄링, 계측 속도를 개선한 후속 프로젝트이다.

- afl-clang-fast나 afl-clang-lto 같은 래퍼 컴파일러를 통해 빌드 시 각 분기점에 추적 코드를 삽입(컴파일 타임 계측)한다.
- 매번 프로세스를 처음부터 다시 로드하지 않고 초기화가 끝난 위치에서 fork()로 복제 실행하여 퍼징 속도를 높인다(Fork Server)

## ## [Jackalope](https://github.com/googleprojectzero/Jackalope)
- Grey-box Fuzzer (바이너리 커버리지 기반, 커스터마이징 특화)
- 소스코드가 없는 Windows, masOS, Linux, Android 환경의 클로즈드 소스 바이너리를 효율적으로 퍼징하기 위해 설계되었다.

- TinyInst를 사용한 바이너리 계측
- 바이너리 형식을 위한 간단한 일반 변형 도구 모음과 문법 기반 변형 엔진 
- -start_servr 및 -server 옵션으로 단일 머신의 멀티스레드, 여러대의 서버간에 커버리지와 크래시를 실시간으로 공유하며 병렬 퍼징을 수행할 수 있다.

## ## [libFuzzer](https://llvm.org/docs/LibFuzzer.html)
- Grey-box Fuzzer (In-process, Coverage-guided)
- LLVM 프로젝트[^8]에 기본 내장된 라이브리 형태의 커버리지 기반 퍼징 엔진이다. 독립된 실행 파일 전체를 외부에서 반복 실행하는 대신, 개발자가 테스트할 함수(API)를 호출하는 진입점을 작성하면 퍼저와 타깃 코드가 하나의 프로세스로 링크되어 동작한다.
[^8]: LLVM 프로젝트: 다양한 프로그래밍 언어를 기계어로 번역하고 최적화하기 위해 만든 오픈소스 컴파일러 및 툴체인 인프라 집합 

- 매번 프로세스를 새로 생성(fork, execve)하지 않고, 단일 메모리 공간 내에서 타깃 함수를 직접 반복 호출한다(In-process 실행) -> 오버헤드가 적고 실행 속도가 빠르다.
- -fsanitize=fuzzer 플래그로 쉽게 활성화되고, ASan, MSan, UBSan등과 결합하여 작은 메모리 오염이나 정의되지 않은 동작을 즉각 감지한다. 

- 같은 메모리 공간을 계속 재사용하기에, 타깃 함수 내부에 전역 변수 상태 오염이나, 메모리 누수가 있으면 퍼징 도중 오작동하거나 OOM으로 종료될 수 있다.

## ## Honggfuzz 
- Grey-box Fuzzer (Evolutionary, Feedback-driven)

- 하드웨어 및 소프트웨어 코드 커버리지를 활용해 입력값을 발전시킨다. 
- 단일 실행 명령만으로 가용 CPU 코어 전체를 활용한다. 실행중인 스레드와 프로세스 간 코퍼스(시드 큐)를 실시간으로 자동 공유한다. 
- 빈 코퍼스(corpus)[^9]에서 시작해도 유효한 입력 데이터셋을 자동으로 구축할 수 있다.
[^9]: 코퍼스(corpus): 퍼저가 테스트를 위해 수집하고 관리하는 유효한 입력 데이터(seed)들의 집합. 퍼징 도중 새로운 커버리지를 발견한 입력값이 계속 추가되며 코퍼스가 성장한다. 

## ## [OSS-Fuzz](https://github.com/google/oss-fuzz)
- Google이 구축/운영하는 오픈소스 소프트웨어를 위한 무료 자동화 퍼징 서비스. 단일 퍼징 엔진이 아닌, 여러 퍼저와 Sanitizer를 결합하여 Google의 대규모 클라우드 인프라에서 24시간 돌아가는 플랫폼

- 백엔드 퍼징 엔진으로 libFuzzer, AFL++, Honggfuzz를 동시에 활용한다. ASab, MSan, UBSan 연동으로 크래시 뿐만 아니라 작은 메모리/정의되지 않은 동작까지 잡아낸다. 
- 크래시가 발견되면 자동으로 중복 제거(Triage)을 거친 뒤, 해당 오픈소스 프로젝트 관리자에게 버그 리포트를 자동으로 발행한다. 패치가 적용되면 해당 입력값을 다시 테스트하여 수정 여부까지 검증한다.
- Google이 오픈소스로 공개한 분산 퍼징 인프라 ClusterFuzz[^10]를 백엔드로 사용한다.
[^10]: ClusterFuzz: 대규모 분산 퍼징 자동화 인프라. AFL++, libFuzzer 등의 개별 퍼징 엔진을 클라우드 가상머신(VM)에서 24시간 통합 관리/운영하는 컨트롤 타워

# # 장점 및 한계
## ## 장점
- 자동화와 객관성: 인간이 코드 리뷰로 놓치기 쉬운 복잡한 상태 전이나 메모리 버그를 자동으로 찾아낸다.
- 낮은 오탐(False Positive): 프로그램을 실행하여, 크래시를 유발하는 입력을 결과로 뱉기 때문에 발견된 버그가 실재로 존재함을 입증한다.

## ## 한계
- 퍼징에서 버그가 나오지 않았다고 프로그램에 취약점이 없다는 것은 아니다.
- 크래시나 메모리 오류를 일으키지 않는 **논리적 취약점**은 탐지할 수 없다.  
논리적 취약점으로는 인증 우회, 검증 누락 등이 있다.
- 상태 기반(이전 입력에 따라 내부 상태가 계속 변하는) 프로그램은 깊은 상태까지 도달하기 힘들다.
- 입력값에 매직넘버나 암호화/체크섬 검증 로직이 존재한다면 무작위 변위만으로는 통과(경로 도달)가 어렵다.
