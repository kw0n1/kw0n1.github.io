# # Broken Access Control
웹 애플리케이션이 사용자 접근 권한을 제대로 관리하지 못하여 발생하는 웹 취약점이다. 유저가 자신에게 허용되지 않은 권한 범위를 벗어나 행동한다면(허가되지 않은 데이터나 기능에 접근) 해당 취약점을 발생시킨다. 

예를 들자면 일반 유저가 관리자 페이지에 접근한다거나(권한 상승, 수직 접근), 쇼핑몰 사이트에서 URL의 파라미터 부분을 조작하여 다른 유저의 데이터에 접근(수평 접근)하는 것이다. 

# # 접근 제어(Access Control)
접근 제어는 **사용자가 허용된 권한 범위를 벗어나 행동하지 못하도록** 제한하는 것이라고 할 수 있겠다. 즉, 사용자/프로그램/프로세스의 특정 요청을 허용하거나 거부하는 것이다. 
접근 제어가 실패하면 일반적으로 무단 정보 유출, 데이터의 수정 및 파괴, 사용자 권한 범위를 벗어난 행동 수행으로 이어질 수 있다. 

---

# # Access Control의 유형
## ## 수직적 접근 제어(Vertical Access Control)
**서로 다른 권한 수준** 사이에서 **낮은 권한의 사용자가, 높은 권한의 기능이나 리소스에 접근하지 못하도록 제한**하는 것이다. 일반 사용자가 관리자에게만 허용되는 계정을 삭제 기능이나 설정을 변경하는 등의 행위를 할 수 없도록 제한하는 것이 해당된다.

이처럼 낮은 권한의 주체가 허용되지 않은 상위 권한의 기능을 사용하게 되는 것을 수직적 권한 상승(Vertical Privilege Escalation)이라고 한다. 

## ## 수평적 접근 제어(Horizontal Access Control)
**동일 수준 권한**을 가진 사용자들 사이에서 **각자 자신에게 속한 리소스에만 접근**하도록 제한하는 것이다. 유저A는 유저A의 정보에만 접근해야하며, 유저B의 정보에는 접근할 수 없어야하는 것이 해당된다. 

이처럼 같은 권한 수준의 다른 사용자가 소유한 리소스에 접근하게 되는 것을 수평적 권한 상승(Horizontal Privilege Escalation)이라고 한다. 

## ## 컨텍스트 기반 접근 제어(Context-Dependent Access Control)
사용자의 권한 수준, 소유 관계 뿐만 아니라 **애플리케이션 상태**나 **사용자 동작 흐름까지 고려**하여 접근 여부를 판단하는 것이다. 각 단계의 전제 조건이 충족된 경우에만 다음 동작을 허용하는 것이 이에 해당한다.

# # Access Control 보안 모델
## ## RBAC: 역할 기반 접근 제어 
Role-Based Access Control. 사용자에게 권한을 직접 부여하는 대신 **역할에 권한을 부여**하고 사용자에게는 역할을 할당하는 방식이다. 

## ## RuBAC: 룰 기반 접근 제어
Rule-Based Access Control. **사전에 정의된 규칙**을 기준으로 접근을 판단한다. 규칙으로는 액세스 시간, IP주소, 다단계 인증 등을 조건으로 사용할 수 있다. 

## ## MAC: 강제 접근 제어
Mandatory Access Control. **주체와 객체에 적절한 보안등급(레이블)**을 **부여**하여, 보안 레이블과 비교(등급을 비교)하여 리소스에 대한 접근을 판단한다. 예를들어 최상위, 상위, 중위, 하위, 최하위와 같이 보안 등급을 만들어 주체와 객체에 부여하고 주체와 객체의 등급을 비교하여 접근을 제어하는 식이다. 

## ## DAC: 임의 접근 제어
Discretionary Access Control. **리소스 소유자의 재량**(객체에 대한 소유권에 기초)으로 사용자의 접근을 판단한다.  
제 3자로부터 부여받은 권한을 나의 재량으로 다른 사용자에게 부여할 수도 있으며, 나에게 주어진 권한이 회수되면 내가 부여한 다른 사람들의 권한도 자동으로 회수된다. 

## ## ABAC: 속성 기반 접근 제어
Attribute-Based Access Control. 사용자와 리소스, 요청 환경이 가진 **속성을 조합한 정책**으로 접근을 판단한다. 속성으로는 사용자의 부서, 직급, 리소스 등급, 요청 시간, 접속 위치 등 다양한 속성을 조건으로 사용할 수 있으며 역할 만으로는 표현하기 어려운 세밀한 정책을 구현할 수 있다. 

## ## ReBAC: 관계 기반 접근 제어 
Relationship-Based Access Control. **주체와 리소스 사이의 관계**를 기준으로 접근을 판단한다. 특정 리소스의 소유자인지, 소유주로부터 공유를 받았는지 등의 관계가 인가 여부의 판단 근거가 된다. 공유 관계가 복잡하게 얽히는 서비스에 적합하다.  

외에도 다른 제어 모델들이 존재한다.

# # Access Control 공격 방법들 
## ## IDOR(Insecure Direct Object Reference)
식별자를 조작하여 다른 사용자의 객체에 접근하는 기법이다. 객체의 소유권과 권한을 검증하지 않기에 일어난다. 해당 취약점으로 자신에게 허용되지 않은 다른 사용자의 정보를 열람하거나, 수정 및 삭제까지도 가능하다. (수평적 권한 상승 방식)  

`GET /order/detail?order_id=1024`로 주문 내역을 확인하는 경우 `GET /order/detail?order_id=1025`로 요청했을 때, 요청을 보낸 사용자의 주문인지 확인하지 않으면 다른 사용자의 주문 내역을 볼 수 있다. 

> 1. 객체를 식별하는 **파라미터의 값**이 순차적 숫자처럼 **쉽게 추측할 수 있는 형태로 노출**  
> 2. 서버가 **요청자의 접근 권한 확인X**  
>
> ▶ 서버가 모든 요청에 대해 요청자가 해당 객체에 접근할 권한이 있는지 직접 확인할 것.

## ## 파라미터 변조(Parameter tampering)
요청이 담긴 권한/식별 정보를 조작하여 서버가 의도하지 않은 동작을 유도한다. 변조 대상에는 쿠키, 폼 데이터, JSON 본문, 헤더 등 사용자가 수정할 수 있는 모든 값이 포함된다. IDOR 또한 식별자라는 파라미터를 변조하는 경우에 해당한다. 

```
POST /api/profile/update
{
  "nickname": "whoami",
  "bio": "hello",
  "is_admin": false
}
```
프로필 수정 시 위와 같은 내용이 서버로 전송된다고 했을 때, is_admin은 역할 속성으로 사용자가 페이지에서 수정할 수 있는게 아니라 서버가 계정 권한 판단 시 참조하는 내부 속성이다. 요청에 담긴 파라미터를 계정 정보에 반영하는 구조라면 is_admin값을 true로 변조할 수 있다. 따라서 is_admin값을 별도 검증 없이 신뢰한다면, 공격자는 자신의 계정을 관리자로 상승시킬 수 있다.

> ▶ 사용자의 요청에 담겨오는 **값을 그대로 신뢰하지 않**을 것  
> ▶ 서버는 중요한 **판단의 근거**를 **요청값이 아닌 세션이나 DB에 저장**해야 함  
> ▶ 요청 본문을 객체에 그대로 반영하지 않고, **사용자가 변경할 수 있는 항목만 선별하여 반영**해야 함 

## ## 강제 브라우징 (Forced Browsing)
애플리케이션이 직접 노출하지 않은 경로나 파일을 직접 추측/탐색하여 접근한다. 공격자는 `https://example.com/admin`와 같이 흔히 사용되는 경로를 브루트 포스(무작위 대입)하거나, 자동화 도구로 여러 경로에 반복적으로 요청을 보내 노출되지 않은 리소스를 탐색할 수 있다. 경로들에 대한 요청자의 권한을 확인하지 않으면, 노출되지 않은 관리자 페이지에 접근할 수 있다. 

> ▶ **모든 요청**에 대해 서버의 **접근 권한 확인**이 필요  
> ▶ **경로가 알려지더라도 권한이 없는 요청은 거부되도록** 구현할 것 

## ## 클라이언트 측 접근 우회(Client-Side Access Control Bypass)
애플리케이션의 접근 제어 로직을 프론트엔드에 배치한 경우 발생한다. 예를 들어, JavaScript(JS)로 권한이 없는 유저에게는 관리자 메뉴 버튼을 숨기는 등의 처리를 해두면 공격자는 `https://example.com/app/admin_getappInfo`에 브라우저에서 실행되는 JS 코드 때문에 해당 부분에 접근할 수 없다. 하지만 브라우저를 거치지 않고 서버에 직접 요청을 보내면 JS의 방해를 받지 안하고 관리자만 접근 가능한 페이지에 접근할 수 있게 된다. 터미널에서 서버로 HTTP 요청을 보내는 curl을 이용하여 `curl https://example.com/app/admin_getappInfo` 명령을 보낼 수 있다.

## ## HTTP 메서드 우회 
요청 메서드를 바꾸어서 인가 검증을 우회하는 기법이다. 웹 요청으로는 GET, POST, PUT, DELETE가 있다. RESTful로 설계된 API의 경우 동일 경로일지라도 조회는 GET, 생성은 POST, 삭제는 DELETE와 같이 수행할 동작을 메서드로 구분한다. 개발 과정에서 일부 메서드는 권한 검증을 적용했지만, 다른 메서드에는 권한 검증을 누락할 경우 취약점이 발생한다.  
예를 들어 `POST /api/admin/user/update` 로 회원 정보 요청했을 때, 서버는 요청자가 관리자 권한인지 확인 후 요청을 처리, 관리자가 아니면 요청을 거부한다. `PUT /api/admin/user/update` 처럼 동일 경로가  PUT 메서드로 들어오는 요청도 처리하도록 구현되었으나, 이에 대한 권한 검증이 누락되었을 경우 공격자는 관리자가 아니어도 다른 사용자의 정보에 손을 댈 수 있게 된다. 

> ▶ 하나의 기능에 접근하는 **모든 경로와 메서드**에 대해 **일관된 권한 검증**이 필요 

## ## 보안 구성 및 정책 설정 오류
접근 제어 로직이 존재하지만 서버의 기본 보안 정책이나 외부 연동 설정을 잘못 구성하여서 의도하지 않게 권한이 오픈된 경우이다. 예를들어, 기본 거부 원칙을 어기고 특정 기능의 접근 권한을 전체 허용으로 방치하거나, CORS(교차 출처 리소스 공유) 설정을 느슨하게 열어두어 신뢰할 수 없는 외부 사이트에서도 사용자 권한을 이용하여 내부 API에 접근해 민감한 데이터를 읽을 수 있는 상황이 해당된다. 


## 메타데이터 및 토큰 조작 
웹 애플리케이션은 사용자가 누구인지, 어떤 권한을 가졌는지 식별하기 위해서 JWT(JSON Web Token), 쿠키, 숨겨진 HTML 필드(Hidden Field) 등의 메타데이터를 주고받는다. 해당 기법은 공격자가 이 값을 위변조하거나 재사용하여 서버의 권한 검증을 속이는 방법이다.  
토큰 재사용은 유효한 인증 토큰을 탈취하여 재사용한다. 토큰에 대한 만료시각이 없거나, nonce값으로 일회성 사용을 강제하지 않거나, 토큰을 특정 세션과 기기에 연결하지 않으면 공격이 성공할 수 있다.

# # Broken Access Control 방지를 위한 권고사항
접근 제어는 사용자가 조작할 수 없는 신뢰할 수 있는 서버에서 구현될 때만 효과가 있다. 사용자의 회면에서 버튼을 숨기는 것과 같은 방법은 개발자 도구나 `curl`과 같은 HTTP로 바로 요청을 보내는 도구들로 우회할 수 있기 때문이다. 

## ## 최소 권한 원칙: 필요한 권한만 준다.
공개된 페이지를 제외한 모든 기능과 데이터는 **기본적으로 접근**을 **차단**(Deny by Default)하고, 허용된 사용자(특별한 경우)에게만 접근을 허용한다.

**역할을 하드코딩하지 않**는다. `if (user == "admin")`과 같이 권한 조건을 직접적으로 작성할 경우, 검증 로직이 누락되기 쉽다. 

## ## 서버에서 모든 요청에 대해 일관되게 권한을 확인한다. 
매번 권한 검사 코드를 따로 짜면 어딘가에는 결함이 생기기 마련이다. **접근 제어 메커니즘은 한 번**만 **구현**하고 애플리케이션 전체에서 **재사용**한다. 

"로그인했는지"만 확인하는 것이 아니라 **비즈니스 규칙[^1]을 도메인[^2] 모델[^3]에 적용**하여, 실제 데이터가 처리되는 도메인 모델(핵심 로직)에서 "이 사용자가 이 데이터의 주인이 맞는지"를 검증해야 한다.  
예를 들어 쇼핑몰의 경우 '본인이 결제한 주문만 취소할 수 있다'는 규칙을 주문 처리 로직에 적용시킨다. 

[^1]: 비즈니스 규칙: 서비스가 정상적으로 돌아가기 위해 반드시 지켜야하는 업무 규칙 및 제약 조건. 본인이 결제한 주문만 취소할 수 있다, 이미 배송이 시작된 주문은 취소할 수 없다 등이 해당된다.
[^2]: 도메인: 소프트웨어가 해결하려는 현실 세계의 문제 영역이다. 쇼핑몰의 경우 주문, 결제, 배송, 회원 등이 해당한다. 
[^3]: 도메인 모델: 도메인을 코드로 만든 것. 자바로 구현했을 경우 주문 기능을 구현한 Order 클래스 등이 해당한다. 

**CORS(Cross-Origin Resource Sharing)**의 **사용**을 **최소화**(신뢰할 수 있는 도메인만 허용)한다. 브라우저는 보안을 위해 다른 사이트가 API를 몰래 호출하지 못하도록 막아두는데, 이를 허용하는 설정이 CORS이다. 개발 과정의 편리함을 위해 모든 외부 사이트의 접근을 허용하면, 공격자가 만든 악성 사이트에 사용자가 접근하는 것만으로도 사용자의 권한을 빌려 API 서버를 호출할 수 있게 된다.

## ## 불필요한 노출을 줄이고 공격 시도를 감시한다. 
폴더 내부 파일 목록이 그대로 노출되지 않도록 **웹서버 디렉토리 목록 표시**를 **비활성화**한다.

백업 파일이나 설정 파일 등 **민감한 파일**은 **웹 루트**(웹 서버 공개 폴더)**에 두지 않아야** 한다. 

API 및 컨트롤러 접근에 대한 **속도 제한**을 **구현**한다. 자동화된 공격 도구를 이용해 짧은 시간 내 과도한 요청이 들어올 경우 차단하여 피해를 최소화한다. 

권한이 없는 사용자가 관리자 페이지나 다른 사람의 데이터에   **접근**하려다 **실패**한 기록(**로그**)를 남긴다. 특정 IP나 계정에서 반복적인 실패가 감지될 경우, 관리자에게 알리도록 한다.

## ## 세션 및 토큰(출입증)의 수명과 폐기를 철저하게 관리한다.
**세션 방식**으로 서버가 출입 명부를 직접 관리할 경우, 사용자가 **로그아웃 시** 서버의 출입 명부에서 해당 **세션 ID를 즉시 삭제**(무효화)한다. 

JWT 토큰 방식으로 출입증에 정보를 담아 발급하는 경우, 서버에서 회수하기가 어렵다. 따라서 토큰의 **수명**(유효기간)을 짧게 설정하여 **금방 만료되도록** 한다. 토큰의 짧은 수명으로 인한 사용자의 불편함을 줄이기 위해 **갱신 토큰(재발급용)을 사용**한다. 권한이 취소(회수)되어야 할 때는 **OAuth 표준에 따라 폐기 절차**를 통해 접근 권한을 취소한다.

> 다른 어려운 기법도 아닌 인간이 만든 오류들이 상위권을 차지하고 있는 것은 놀라웠다. 처음 프로그램을 설계하는 단계부터 보안에도 신경을 많이 써야할 것 같았고, 개발자 또한 보안을 신경쓰면서 개발하면 굉장히 복잡해질 것 같다는 생각이 들었다. 하지만 고려해야겠죠?
